# Deployment Guide

## Recommended Target

This is a Django backend project. Deploy it to a Python WSGI/ASGI host such as Render, Railway, Fly.io, or a VPS with Gunicorn and Nginx.

Netlify can host a future static frontend, but it is not the right target for the full Django backend.

For the Hong Kong VPS first-launch baseline, use `docs/production-deploy-baseline.md` and `docs/production-deploy-checklist.md` as the operator runbook.

For repeat VPS deploys, use the repository deploy scripts from the `ubuntu` account:

```bash
cd /srv/animeimages
./scripts/pre_deploy_check.sh
./scripts/deploy.sh
```

Do not run Git as root in `/srv/animeimages`. The working tree should remain owned by `ubuntu:ubuntu`, and production-only values should live in `/srv/animeimages/.env.production`, not in `djangoProject/settings.py`.

## Production Git SSH

Production uses a dedicated SSH host alias:

```text
git@github-animeimages:Daiobs/AnimeImages.git
```

The alias is configured in:

```text
~/.ssh/config
```

Example:

```sshconfig
Host github-animeimages
  HostName github.com
  User git
  IdentityFile ~/.ssh/animeimages_deploy
  IdentitiesOnly yes
```

Do not replace this remote with default github.com SSH unless the deploy key is configured.

## Production Filesystem Ownership

Production deploys use a fixed application ownership model:

```text
/srv/animeimages:
  owner: ubuntu
  group: ubuntu
```

Current production Gunicorn listens on TCP `127.0.0.1:8000` and does not use `/run/animeimages`. A future Unix-socket hardening target may use `/run/animeimages` managed by systemd `RuntimeDirectory`, but that topology is not currently deployed.

`deploy.sh` and `pre_deploy_check.sh` check the ownership of `/srv/animeimages` before Git operations. They do not recursively repair ownership. If the application directory owner or group is wrong, the deploy must fail and the operator must repair it explicitly:

```bash
sudo chown -R ubuntu:ubuntu /srv/animeimages
```

This keeps permission drift visible instead of hiding it during deploy. Do not run Git, dependency installation, migrations, or collectstatic as root inside `/srv/animeimages`.

Static assets are separate from the application ownership gate. `staticfiles/` is generated by `collectstatic` and must remain readable by Nginx, but deploy scripts do not use recursive ownership checks under `/srv/animeimages`; a readable `staticfiles/` tree should not cause the application directory ownership check to fail.

For small operational checks after a manual change:

```bash
cd /srv/animeimages
./scripts/restart.sh
./scripts/health_check.sh
```

`deploy.sh` deploys `main` by default. For a staging-only branch deploy, set `DEPLOY_BRANCH` explicitly:

```bash
DEPLOY_BRANCH=codex/production-stabilization-v0.1 ./scripts/deploy.sh
```

## Required Environment Variables

Start from `.env.example.production` if you keep configuration in the project root. Runtime reads the project-root `.env` plus deployment environment variables; the example files are templates only.

- `DJANGO_SECRET_KEY`: long random production secret
- `DJANGO_DEBUG=False`
- `DJANGO_ALLOWED_HOSTS`: comma-separated hostnames
- `DJANGO_DATABASE_URL`: PostgreSQL connection URL, for example `postgresql://user:password@127.0.0.1:5432/animeimages`
- `DJANGO_CACHE_URL`: shared Redis URL used by rate limits and validated provider caches
- `DJANGO_SECURE_SSL_REDIRECT=True` when HTTPS is available
- `DJANGO_SESSION_COOKIE_SECURE=True` when HTTPS is available
- `DJANGO_CSRF_COOKIE_SECURE=True` when HTTPS is available
- `DJANGO_TRUST_X_FORWARDED_PROTO=True` when Nginx terminates HTTPS and proxies to local Gunicorn
- `DJANGO_CSRF_TRUSTED_ORIGINS=https://your-domain.example` for the public HTTPS origins that serve the admin and download pages
- `DJANGO_SECURE_HSTS_SECONDS=31536000` only after confirming HTTPS for the full site
- `DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=True` only if all subdomains are HTTPS-only
- `DJANGO_SECURE_HSTS_PRELOAD=True` only if the domain is ready for browser preload

## Runtime

Use a production server instead of `runserver`.

Example:

```bash
gunicorn djangoProject.wsgi:application
```

Add `gunicorn` to dependencies when a deployment target is chosen.

### Current Production Topology

The current production service runs Gunicorn as `www-data`, binds TCP `127.0.0.1:8000`, and receives traffic from Nginx on that local address. The application checkout remains owned by `ubuntu:ubuntu`.

Current audited systemd shape:

```ini
[Service]
User=www-data
Group=www-data
WorkingDirectory=/srv/animeimages
EnvironmentFile=/srv/animeimages/.env.production
UMask=0007
ExecStart=/srv/animeimages/.venv/bin/gunicorn djangoProject.wsgi:application --bind 127.0.0.1:8000 --worker-class gthread --workers 2 --threads 4 --timeout 60 --access-logfile - --error-logfile -
Restart=on-failure
RestartSec=5
```

The repository copy is `ops/systemd/animeimages.service`. Repository changes do
not install or restart the production unit.

Gunicorn runs as `www-data`, while the application checkout remains owned by `ubuntu:ubuntu`. The Web process needs read access to application files and approved local Git refs, but it must not own the checkout, run `git fetch`, or receive the production deploy key.

Configure the deployment platform or load balancer with:

- `/health/live/` for process liveness. It does not contact external services.
- `/health/ready/` for traffic readiness. It verifies the configured Django cache/Redis and database with a real round trip.

Both endpoints disable response caching and expose only component availability, not connection strings or exception text. A failed dependency makes readiness return HTTP `503`.

When Nginx terminates HTTPS, forward the original scheme and request id:

```nginx
upstream animeimages_app {
    server 127.0.0.1:8000;
}

location / {
    proxy_pass http://animeimages_app;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Request-ID $request_id;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

With `DJANGO_TRUST_X_FORWARDED_PROTO=True`, Django uses `X-Forwarded-Proto: https` to build secure URLs and apply HTTPS-aware CSRF/session behavior while Gunicorn stays behind local Nginx.

The current direct readiness target is:

```bash
HEALTH_CHECK_URL=http://127.0.0.1:8000/health/ready/ ./scripts/health_check.sh
```

### Future Recommended Hardening Target (Not Currently Deployed)

A future reviewed infrastructure change may replace the local TCP listener with a systemd-managed Unix socket. This is not the current production topology and must not be treated as already deployed.

Future systemd shape:

```ini
[Service]
User=www-data
Group=www-data
WorkingDirectory=/srv/animeimages
EnvironmentFile=/srv/animeimages/.env.production
RuntimeDirectory=animeimages
RuntimeDirectoryMode=0750
UMask=0007
ExecStart=/srv/animeimages/.venv/bin/gunicorn djangoProject.wsgi:application --bind unix:/run/animeimages/gunicorn.sock --pid /run/animeimages/gunicorn.ctl --workers 2 --timeout 120
Restart=on-failure
RestartSec=5
```

In that future topology, systemd creates `/run/animeimages` on service start and Nginx uses:

```nginx
upstream animeimages_app {
    server unix:/run/animeimages/gunicorn.sock;
}
```

The change requires coordinated systemd and Nginx updates, service restart, socket permission validation, and readiness smoke tests. This documentation PR does not apply any of those server changes.

## Database

SQLite is acceptable for local development. Production should use PostgreSQL or another managed relational database.

Before switching databases:

1. Add database configuration through `DJANGO_DATABASE_URL`.
2. Run migrations on a staging database.
3. Verify upload and media paths.

## Media Files

User uploads and downloaded files live under `media/` locally. For production, use persistent storage or object storage. Do not rely on ephemeral container disk for important uploads.

Django only appends the development `MEDIA_URL` route while `DEBUG=True`. In production, configure Nginx, private object storage, or another explicit media delivery layer. Do not expose the whole `media/` directory as a public fallback route.

The Xiaohongshu download endpoint returns a browser ZIP download instead of writing to arbitrary server paths. Keep this boundary in production; do not allow untrusted users to choose absolute server filesystem paths.

Recommended production settings:

```text
XHS_ALLOW_SERVER_SAVE=False
XHS_ALLOW_ABSOLUTE_SAVE_PATH=False
DOWNLOAD_ASYNC_TASKS_ENABLED=False
```

The in-memory background task implementation is intentionally local-only. With production async tasks disabled, the browser automatically uses the synchronous temporary ZIP response. Before re-enabling asynchronous progress in production, replace task state and execution with Redis plus Celery/RQ and store completed archives in a controlled temporary/object-storage location.

Public download endpoints use shared-cache counters for per-IP frequency, per-IP concurrency, daily request count, and daily output bytes. Configure the limits from the project-root `.env` or deployment environment variables. Browser-direct/SW transfers do not acquire server-side media concurrency slots merely to establish an identity.

### Trusted client address

The shared resolver in `services/rate_limits.py` is used by rate limits, anonymous
rollout, GeoIP, request observations and IP-bound resource handoffs. Its default
is the socket peer (`REMOTE_ADDR`), not a client-supplied proxy header. To accept
X-Forwarded-For, **both** the existing switch and explicit proxy ranges are
required. The ranges use the existing `env_config.runtime_list` reader; no
`settings.py` change is required.

For a verified single local Nginx -> IPv4-loopback Gunicorn deployment, a future
authorized deployment can migrate from `False` / empty ranges to:

```text
DOWNLOAD_TRUST_X_FORWARDED_FOR=True
DOWNLOAD_TRUSTED_PROXY_CIDRS=127.0.0.1/32
```

Do not apply this example to an unverified topology. Trust `::1/128` only if it
is an actual proxy peer. Do not trust all private networks; universal ranges
(`0.0.0.0/0`, `::/0`) or malformed CIDRs fail closed. Empty ranges also trust
nothing, even when the switch is true. Keep the origin's network access controls.

The managed Nginx configuration appends its peer using
`$proxy_add_x_forwarded_for`. Starting at the actual socket peer, the application
walks right to left only through explicitly trusted proxies and stops at the
first untrusted address. It ignores X-Real-IP and Forwarded for identity.
Malformed addresses at the trusted boundary, missing headers, or a trusted
chain requiring over 2048 characters / 20 entries to resolve fall back to the
socket peer; they never skip a bad boundary to accept an earlier claim. Once
the untrusted client boundary is reached, its left-hand claims are ignored,
including oversized prefixes, so client padding cannot choose the proxy bucket.
IPv6 is canonicalized,
IPv4-mapped IPv6 becomes IPv4, and scoped/port-bearing address strings are rejected.

If a CDN/load balancer is added, first verify its forwarding behavior, narrow
proxy ranges and origin bypass controls. A DNS provider name alone does not
prove proxying. Do not add all upstream networks on speculation.

Anonymous rollout now uses this same address without User-Agent. Authenticated
rollout continues to use the user ID; disabled/staff/gray/public modes and
percentages are unchanged. IP rollout is gradual exposure, not strong identity
or an exact user quota: users behind one egress can share a bucket, and changing
networks can change it. Migration may change short-lived counter keys, buckets
and IP-bound tokens. Let old records expire and require normal re-parsing when
needed; do not clear global caches or keep accepting spoofable legacy identities.

Read-only observation on 2026-10-19 found the installed project Nginx site
forwarding to `127.0.0.1:8000`, with X-Real-IP=`$remote_addr` and appended XFF;
Gunicorn runs as `www-data` and binds that loopback address. The service's
environment file records `DOWNLOAD_TRUST_X_FORWARDED_FOR=False`, and no matching
unit-level override was observed. Local DNS resolved the hostname to the recorded
origin address. Full `nginx -T` and live process environment access were denied,
so loaded include/edge behavior and origin bypass restrictions are **not fully
verified**. These are deployment prerequisites, not claims of production fixes.
This task changed no production configuration and sent no public spoofing probes.

The five candidate/selection descriptor endpoints also require the updated
managed media snippet; see [Nginx baseline and acceptance](../ops/nginx/README.md).
Installing application code alone does not remove the old Nginx 404 boundary.

For this reverse-proxy deployment, leaving proxy trust disabled or omitting the
correct trusted CIDRs can make clients share the proxy socket identity (for
example, loopback), combining their rate-limit counters and anonymous rollout
buckets. This does not mean every production topology has one client identity.
Before enabling trust, confirm the effective proxy chain and origin access
controls, then select only the narrow CIDRs justified by that topology.

Use the existing fixed-SHA release checklist for one controlled migration of
application code, proxy-trust configuration and the updated media snippet.
Prepare and review the candidate configuration and corresponding version/backup
set before switching; validate syntax and preserve reviewed site-specific Nginx
additions. Code-only or partially configured intermediate states are not a
completed release. Do not infer effective runtime configuration from repository
defaults or the readable files alone.

Acceptance must confirm that two controlled clients retain separate identities
and quotas, a forged XFF prefix/X-Real-IP or changed User-Agent cannot choose
their identity or rollout bucket, and disabled/staff/0% rollout restrictions
remain intact. Verify all five exact business APIs listed in the Nginx runbook
reach the application using bounded upstream request records, retain method,
CSRF and resource-authorization rejections, and leave unknown/upload/subpaths
blocked. Keep the short-lived identity/token expiry behavior described above;
do not clear global caches to make the migration appear successful.

Rollback must restore a reviewed compatible combination of application SHA,
proxy-trust configuration and snippet version, followed by the same identity
and route checks; do not roll back only one component and assume compatibility.
These instructions complete migration preparation only. Production execution,
configuration changes, snippet installation and reload still require separate
authorization; production is not marked fixed by this documentation update.

The image preview proxy is also an outbound bandwidth path and has separate controls:

```text
PREVIEW_RATE_LIMIT_PER_MINUTE=60
PREVIEW_DAILY_REQUEST_LIMIT_PER_IP=1000
PREVIEW_GLOBAL_DAILY_REQUEST_LIMIT=10000
PREVIEW_DAILY_BYTES_LIMIT_PER_IP=1073741824
PREVIEW_GLOBAL_DAILY_BYTES_LIMIT=21474836480
```

These are initial safety defaults, not capacity guarantees. Tune them from observed traffic and server bandwidth. Redis failure makes protected preview requests fail closed with HTTP `503`.

Ultra-HD access has capability and runtime switches:

```text
ULTRA_HD_PROVIDER_ENABLED=True
ULTRA_HD_PUBLIC_ACCESS_ENABLED=False
TIANTIANJIEXI_PROVIDER_ENABLED=True
KUKUTOOL_PROVIDER_ENABLED=True
```

TianTianJieXi is the preferred Douyin ultra provider when credentials are configured. Keep account credentials only in server environment configuration, never in source control or copied logs. KuKuTool remains fallback/race backup and still requires staging validation because it depends on an external upstream/protocol path. Production must provide either Node.js 18 or newer through an explicit `KUKUTOOL_NODE_BINARY`, or an internal `douyin-source-resolver` endpoint through `KUKUTOOL_SIDECAR_BASE_URL`; it does not search the system `PATH` or a user's Codex runtime.

Daily public/staff access is controlled from `/admin/provider-settings/`, not by flipping `.env` on every rollout. Production Redis is also used for provider single-flight, short failure caching, validated results, and global upstream concurrency counters. Keep `DJANGO_CACHE_SOCKET_CONNECT_TIMEOUT` and `DJANGO_CACHE_SOCKET_TIMEOUT` below the foreground budget so a cache outage cannot pin a request. The current bounded thread pools remain available as an interim deployment model. For sustained heavy provider traffic, move resolution to a long-lived sidecar or Celery/RQ so Django workers never own long subprocess lifecycles.

TikHub and country-aware API routing are retained only as dormant research code. They do not affect the active synchronous ultra-HD path.

## Daily Provider Validation Candidate

The repository includes inactive
`ops/systemd/animeimages-provider-validation.service` and `.timer` candidates.
Merging them does not install or enable production scheduling. The command is
safe-defaulted by database `daily_enabled=false`, selected keys
`["health_ready"]`, and environment email delivery disabled. SMTP passwords,
real recipients and approved public sample URLs must be configured only in a
separately authorized production activation.

Admin save-time validation is only the first gate. Every scheduled sample is
revalidated before external execution, including DNS resolution where every
resolved address must remain public; Staff access never authorizes private or
metadata endpoints. Production email delivery also rejects console, dummy,
locmem, and filebased backends, and an unimportable backend is never considered
configured. A notification is marked sent only after an allowed backend
confirms one delivery.

Before installation, follow the ordered activation checklist in
`docs/admin-provider-health-tests.md`. In particular: back up and migrate the
database, retain the disabled DB gate while samples are entered, validate
`--dry-run`, run a no-email canary, validate SMTP separately, inspect the Admin
report, verify timezone and units, then enable the timer and only finally open
the daily DB gate. No deployment, restart, `daemon-reload`, timer enablement or
SMTP setup is performed by the Asset 3 development task.

## SSH Managed Release Channel

`ops/managed-release/README.md` defines the separately installed, manually
approved SSH release channel. It keeps `ubuntu` as the non-root deployment user,
adds only exact animeimages stop plus a root-owned launcher run as www-data,
and retains the existing three exact systemctl deployment rules. The optional
managed probe mode uses the existing reviewed `deploy.sh`; it does not grant a
root shell, root deployment script or general run-as permission.

Every release requires an approved full target SHA and a new maintenance
window. Main merges never deploy automatically. Bootstrap requires one explicit
administrator installation from a digest-verified frozen bundle; repository
merge alone installs nothing. This SSH channel does not enable the Web
executor, change `.env.production`, or install its helper/unit/sudoers.

## Admin Release Management

`/admin/release-management/` shows the current Git branch, commit, matching tag, the locally cached `origin/main`, latest tags, readiness status, and recent release deployment jobs. Release Management v1 only deploys `main`; tags remain visible for planning and audit, but the UI and POST endpoint do not create tag deployment jobs.

Production Web requests only read local Git refs. The release page has no remote-refresh control, and the `www-data` Web process must not run `git fetch`. Local `origin/main` and Tag refs are refreshed by the `ubuntu` deployment workflow or a separately controlled operations task:

```text
RELEASE_MANAGEMENT_GIT_TIMEOUT_SECONDS=6
```

Because `/srv/animeimages` is owned by `ubuntu:ubuntu` while Gunicorn runs as `www-data`, configure the exact production repository as a system-level Git safe directory before enabling the page:

```bash
sudo git config --system --add safe.directory /srv/animeimages
```

Do not use a wildcard safe-directory entry and do not change repository ownership for the Web process. If this setting is missing, the release page reports the `dubious ownership` error and remains unable to create a deployment job.

Creating a main deployment reads the locally cached `origin/main`, stores its exact commit in `job.target_sha`, and records a `ReleaseDeployJob`. It does not fetch remote refs in the Web request. The database permits at most one pending/running job. Long deployment and restart work must stay outside the Django request thread.

Release Management v1 is record-only by default after merge and the first production deployment. The production environment example leaves the executor empty. Without an executor, a release request is recorded as `pending` and does not deploy or restart anything automatically:

```text
RELEASE_MANAGEMENT_EXECUTOR_COMMAND=
# Enable only after the root-owned helper, systemd unit, and sudoers rule have
# been installed and independently tested on the production server.
# RELEASE_MANAGEMENT_EXECUTOR_COMMAND="/usr/bin/sudo -n /usr/local/sbin/animeimages-release-submit {job_id}"
```

Set `RELEASE_MANAGEMENT_EXECUTOR_COMMAND` in `/srv/animeimages/.env.production` only after the root-owned helper, systemd one-shot unit, sudoers rule, service runtime user, application and virtualenv paths, and filesystem permissions have been independently verified on the production server. Example production configuration must not enable the executor by default.

The only accepted executor argv is `/usr/bin/sudo -n /usr/local/sbin/animeimages-release-submit <current-job-id>`. Release Management rejects direct `systemctl`, direct `deploy.sh`, shell wrappers, alternate paths, missing `-n`, wrong IDs, and extra arguments. The request waits only for the root-owned helper to submit systemd work; it never waits for deployment, migration, restart, or health check completion.

Repository templates and the non-installing validator live in `ops/release-executor/` and `scripts/validate_release_executor.sh`. The production installation must use these fixed paths and permissions:

```text
/usr/local/sbin/animeimages-release-submit         root:root 0755
/etc/systemd/system/animeimages-deploy@.service   root:root 0644
/etc/sudoers.d/animeimages-release                root:root 0440
```

Neither `ubuntu` nor `www-data` may modify those installed files. The sudoers rule grants `www-data` only the fixed helper, never direct or wildcard `systemctl`, shell, Git, or `deploy.sh` access. Do not authorize a script under `/srv/animeimages` through sudo. Follow `ops/release-executor/README.md` for static validation, installation, `visudo -cf`, `systemd-analyze verify`, `daemon-reload`, a controlled pending-job test, `journalctl`, final enablement, and immediate disablement.

The one-shot reuses the existing `ubuntu` deployment workflow. Because `scripts/restart.sh` performs the current exact service restart/status operations through sudo, verify that production's existing deployment-user sudo boundary works non-interactively before enabling the executor. This template does not grant `ubuntu` broader privileges; stop for a separate least-privilege review if the existing boundary is insufficient.

Current execution support is intentionally conservative:

- Only `main` deployment jobs can be created or executed in v1.
- The executor passes `DEPLOY_TARGET_SHA=job.target_sha` to `scripts/deploy.sh`.
- After fetch, `deploy.sh` verifies that the SHA is reachable from `origin/main`, resets to that exact SHA, and fails unless the final `HEAD` equals `job.target_sha`.
- Tag/commit switching remains disabled until migration-aware rollback policy and safe target selection are implemented.
- Migration rollback is not automatic. Operators must review migration safety before reverting application code.

## Rollback

To disable Release Management execution immediately, clear `RELEASE_MANAGEMENT_EXECUTOR_COMMAND` in `.env.production` and restart Gunicorn so the Web process reloads the empty value. This stops new submissions but does not cancel a one-shot that systemd already accepted; inspect its unit and journal before taking further action.

Release Management v1 cannot deploy an older Tag or arbitrary commit. The durable rollback path is a reviewed revert merged into `main`, followed by the normal deployment workflow.

Keep each deployed version tied to a Git commit. If deployment fails:

1. Revert the faulty change through the reviewed `main` workflow.
2. Re-run migrations only if rollback migrations are safe.
3. Confirm `check`, smoke URLs, and logs.

### Download audit migration compatibility

The download audit split (`0030` / `0031`) keeps `DownloadRequestLog` for the
existing business records and moves phase/client observations to
`DownloadAuditEvent`. Do not deploy the original PR #132 migration alone:
its four non-null columns lacked persistent database defaults. Corrected `0030`
is safe for the PR #131 ORM even before `0031`; `0031` also repairs databases
that already applied the original `0030`.

Apply migrations while application writers are stopped using the existing
release procedure. `0031` transfers audit rows atomically, preserving their IDs,
timestamps and all scalar fields. It checks the copied rows before removing the
old copies, then repairs the event sequence. Existing signed audit receipts keep
their preparation IDs. The transfer takes a PostgreSQL table lock; budget for
the actual history size during the approved maintenance window.

For an explicitly authorized rollback to PR #131 (`8d91d52`), restore its code
and corresponding static assets but retain the upgraded database. Do not reverse
`0030` or `0031`, restore an older business database, or fake migration records.
Old ORM inserts use the persistent empty database defaults; old readers do not
see the separate phase/client events. A schema reversal with event history is
explicitly refused. Returning to the fixed code reads the retained events again.
The optional business-log ID is a historical correlation without a foreign key,
so old-code pruning can delete its business rows without blocking or deleting
the separate observations.
Phase events do not mirror terminal success, failure or cancellation into the
business table. At most one trusted dispatch row per attempt remains for routing
and control-execution feedback; current legacy statistics and policy learning
exclude rows linked by `legacy_log_id`. Download counts, observed completion and
transfer bytes come from `DownloadAuditEvent`, not dispatch success.
Both log tables use the existing `prune_observability_logs --days` retention
window; Provider administration audit retention is unchanged. This compatibility
note does not authorize a release or rollback.

Production baseline v0.1 should be tagged only after smoke passes:

```bash

```

For an explicitly approved emergency manual rollback outside Release Management only, record the temporary state before resetting to a known-good commit. Review migration safety first, and restore the checkout to reviewed `main` before the next routine deploy or Release Management operation:

```bash
cd /srv/animeimages
git fetch origin --tags
git reset --hard <known-good-commit-or-tag>
source .venv/bin/activate
set -a
source /srv/animeimages/.env.production
set +a

python manage.py collectstatic --noinput

```

Do not switch the filesystem back to `main` without completing a normal deployment. Once the reviewed revert is merged, run the standard `main` deployment so code, dependencies, migrations, static assets, service state, and health checks move together.
