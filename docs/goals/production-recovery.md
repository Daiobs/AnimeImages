# 目标：生产恢复运转（2026-10-21，协调人：Claude）

## 一句话目标

让生产稳定运行最新的 main。并且每个平台的真实样本，按“解析 → 默认清晰度下载”在生产上连续两轮通过。

## 完成条件（全部满足才算完成）

1. 生产运行的提交，是合入本目标全部 PR 之后的 main。记录这个 SHA。
2. 下文定义的生产冒烟连续两轮全部通过，两轮至少间隔 30 分钟，结果记进本文件的进度日志。
3. 本目标开出的 PR 已经处理完：
   - L1 已合并；
   - L2 已由 Human 审阅后合并，或在进度日志里明确列为“等待审阅”并暂停。
4. 最终 main 上必需的 CI 检查全绿，`python manage.py test contracts` 也通过。
5. 进度日志写清楚：做了什么、证据是什么、哪些没做以及原因。

## 生产冒烟（“运转”的定义）

**样本**

- 每个平台选 1 个公开样本：小红书图文、小红书视频、抖音视频、B 站视频。如果生产开放了 YouTube，再加 1 个。
- 样本在 M0 选定，写进本文件，之后不再更换。

**每个样本的检查**

- 匿名访问生产首页的公开解析接口，与普通用户相同，结果页必须有结果。
- 默认清晰度的下载要完整：收到的字节数与声明一致，文件容器能识别。
- 抖音“超清”打开（用户默认设置）。
- B 站走服务端附件下载（INV-03、INV-04）。

**限制**

- 每轮每个平台最多 1 次解析、1 次完整下载，样本之间不并发。
- 不登录 Staff，不改生产数据，不记录密钥、Cookie 或令牌。

**实现**

- 写一个只读脚本，例如 `tools/production_smoke.py`（L1），只调用公开接口。
- 输出每个样本是否通过；失败要写原因（HTTP 状态、接口返回、字节数）。

## 检查点

### M0 · 核实现状（只读，不改业务代码）

1. 记录生产当前运行的 SHA，以及相关开关的取值。只记取值，不记密钥。
2. 选定样本，写好冒烟脚本，在生产上跑一轮。
3. 把失败清单写进进度日志。
4. 把本文件提交为 `docs/goals/production-recovery.md`，作为单独一个 L0 PR，CI 全绿后合并。之后的进度都记在这个文件里。

### M1 · 发布 main

1. 发布前确认：最新 main 的 CI 全绿；托管发布流程里的回滚点可用。
2. 用现有的托管发布流程，把当前 main 发布到生产。
3. 发布后立即跑一轮冒烟。
4. 如果冒烟结果比发布前更差：立刻回滚，然后暂停并汇报。
5. **授权：** Human 已在 2026-10-21 确认，由执行者用现有托管发布流程完成 M1 和 M3 的生产发布，不必再请示。授权只覆盖发布已合并的 main 和按流程回滚，不包括修改生产配置、`.env`、数据库或 nginx。

### M2 · 修复剩余的阻塞问题

- 只修 M1 之后冒烟仍然失败的项。每个问题一个小 PR，带回归测试；能用契约就用契约。
- B 站：如果生产上天天兜底能完成解析和下载，Native 返回 412 就不算阻塞。记为后续（T10），不在本目标内做。

### M3 · 收尾

1. 发布包含 M2 修复的 main。
2. 冒烟连续两轮通过。
3. 在进度日志里写最终总结。

## 约束

- **不变量和契约就是规格：**
  - 不得削弱、回退或绕开。
  - 不新增“失败一次就永久停用、只能人工恢复”的状态（INV-02）。
- **禁止改动的范围：**
  - 两个 Worker 协议文件（G1）。
  - 生产的 `.env`、数据库、nginx 配置、仓库设置和分支保护。确实需要改时，暂停并请 Human 处理。
- **PR 规则：**
  - 一个问题一个 PR。描述第一段写“用户可见行为：之前 → 之后 → 不变量编号”，并写明风险等级。
  - L1 在 CI 全绿后可以自己合并。
  - L2 开出 PR 后，这一项暂停，等待审阅；不要添加 `human-approved` 标签。
- **推送：** 先在本地跑完受影响的测试再推送，不要反复推送半成品（CI 按分钟计费）。
- **范围：** 发现范围外的问题，只记进进度日志的“后续”部分，不开新工作。
- **敏感信息：** PR、日志和进度记录里都不写密钥、Cookie 或令牌。

## 暂停条件（暂停并写明原因）

- 需要 L2 审阅、修改生产配置，或者要改不变量和契约。
- 同一个检查点连续 3 次修复尝试仍然失败。
- 发布后冒烟变差，已经回滚。
- 需要登录 Staff、会明显多消耗付费额度，或者需求本身不确定。
