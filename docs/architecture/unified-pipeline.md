## 0. 总体结构

```
平台链接
  → 路由：后台配置的 Provider 链（A1）
  → Provider 适配器：唯一允许出现平台差异的地方
  → 统一结果
  → 页面展示
  → 用户选清晰度
  → 交付规则：只看资源事实
  → 浏览器保存（服务器只处理两种例外）
```

三条硬规则：

1. **平台差异只出现在 Provider 适配器里。** 路由、展示、交付、文件名的代码里，不出现按平台名、Provider 名或资源 ID 前缀做的判断。
2. **展示和交付只读统一结果，** 不读 Provider 的原始返回。
3. **交付方式只由变体的事实决定，** 不由来源决定。

适配器放在内核目录之外（例如 `xhs_download/services/provider_adapters/`）。内核不导入任何平台或 Provider 代码。

## 1. 统一结果模型

### 1.1 作品（Work）

| 字段 | 含义 |
|---|---|
| `source_url` | 规范化后的作品链接 |
| `work_id` | 平台上的作品编号，没有标题时用于文件名 |
| `platform` | 平台标识，由路由填写，不由 Provider 填写 |
| `title` | 短标题，用于页面标题和文件名 |
| `description` | 正文，不含话题 |
| `topics` | 话题列表 |
| `author` | 作者名 |
| `cover_url` | 封面 |
| `duration_seconds` | 视频时长，可以为空 |
| `items` | 有序的内容项列表，至少 1 个 |
| `groups` | 内容项之间的关系，例如实况照片的“图片＋视频” |
| `provider` | 实际产出这份结果的 Provider，由路由填写 |
| `completeness` | `final` 或 `provisional`。`provisional` 表示之后可能被更好的结果替换，例如抖音超清晚到 |
| `field_sources` | 每个字段由谁提供（Provider 本身，或我们的补充探测）。工作台据此显示字段覆盖（A2） |

### 1.2 内容项（Item）

内容项是作品里的一个可下载对象：一张图、一个视频或一段音频。

| 字段 | 含义 |
|---|---|
| `item_id` | 作品内唯一的编号 |
| `kind` | `image`、`video` 或 `audio` |
| `index` | 在作品中的顺序，从 1 开始 |
| `variants` | 同一内容的不同清晰度或格式，至少 1 个 |
| `default_variant` | 默认选中的变体，由 1.4 第 2 条算出，适配器不指定 |

### 1.3 变体（Variant）：交付需要的全部事实都在这里

| 字段 | 含义 |
|---|---|
| `variant_id` | 编号 |
| `url` | 资源地址 |
| `container` | `mp4`、`webm`、`jpg`、`webp`、`m4a` 等，是真实扩展名的来源 |
| `height`、`width`、`fps`、`bitrate` | 可以为空。Provider 明确给出的分辨率标签（例如 `1080P`、`2160P`、`1080P+`）可以把 `height` 设为标签里的数字；`原画`、`高清`、`4K` 之类不可以 |
| `quality_label` | 显示名，例如 `1080p`、`原画`。没有时按高度生成；高度也没有时显示“默认清晰度” |
| `is_original` | 是否为原画/源文件，默认变体按它优先 |
| `size_bytes`、`size_exact` | 大小，以及它是精确值还是估计值 |
| `tracks` | `unknown`（默认）、`av`（音视频完整）、`video_only` 或 `audio_only`。上游或平台没有说明时就是 `unknown`；图片不适用，保持默认值 |
| `merge_with` | `video_only` 时要合并的音频变体，必须是同一作品里的 `audio_only` 变体 |
| `required_headers` | 下载时必须带的请求头名称，例如 Cookie、鉴权头或上游指定的自定义请求头。上游明确列为必须的请求头都算，包括常规请求头；上游只是带了 User-Agent、Accept、Referer、Origin 等常规请求头的值，不算（INV-03）。值只保存在服务端，不下发给浏览器 |
| `browser_fetchable` | `true`、`false` 或 `unknown`：浏览器能否不带特殊请求头直接读取（包括 CORS）。上游声明链接绑定 IP，或声明需要请求上下文却没有给出时，写 `false` |
| `drm` | 上游标明有 DRM 时为 `true`，默认 `false` |
| `segmented` | 由分片清单或分片组成时为 `true`（HLS、DASH 分片等），默认 `false` |
| `request_method` | 下载请求的方法，默认 `GET`。上游要求其他方法（例如 POST 加请求体）时如实填写；请求体的值不进入统一结果 |
| `expires_at` | 链接过期时间，可以为空 |
| `host_policy` | 跳转时允许的下载主机后缀，由适配器给出。为空表示任意通过逐跳安全检查的公网 HTTPS 主机（通用来源用空列表）；不为空时，每一跳都必须匹配其中一个后缀（D-06） |

### 1.4 不变式（契约测试逐条检查）

1. 每个作品至少有一个内容项，每个内容项至少有一个变体，`default_variant` 必须是其中之一。
2. 默认变体选质量最高的：可下载的变体优先（不命中第 3 节第 0 条），其次原画/源文件，再比高度，再比码率，最后比大小；完全相同时按适配器给出的顺序（INV-03）。用户可以改选。
3. 缺失的字段就记为缺失：不能用 `video`、`原始文件` 之类的占位值当清晰度，不能用平台名或“视频”之类的词当标题，大小不能是 0。
4. `video_only` 的变体必须有 `merge_with`，否则不能作为默认变体；视频内容项的默认变体也不能是 `audio_only`。`tracks = unknown` 的变体可以作为默认变体。
5. 适配器以外的代码，不得读取 Provider 的原始返回。
6. URL 路径以 `.m3u8`、`.mpd` 或 `.m4s` 结尾的变体必须标为 `segmented`。
7. `request_method` 必须是大写的 HTTP 方法名。

不满足 1～4、第 6 或第 7 条的结果，路由按 `invalid_result` 处理，并记下第一条违反项作为诊断码。

## 2. Provider 接口

### 2.1 调用

```
parse(source_url, budget) → Work | Failure
```

- `budget` 是调用方给的时间预算。适配器要么在预算内返回，要么返回 `timeout`。
- **适配器负责：**
  - 调用上游；
  - 把返回映射成统一结果；
  - 填写 `host_policy` 和 `required_headers`；
  - 在 `field_sources` 里标明每个字段的来源。
- **适配器不负责：** 交付方式、文件名、授权、限流、计费。这些都在管线里统一处理。
- 适配器抛出异常或返回其他类型，按 `invalid_result` 处理。

### 2.2 失败类型（只有这五种）

| 类型 | 含义 | Provider 链的行为 |
|---|---|---|
| `unsupported` | 这个 Provider 不支持该链接 | 直接试下一个 |
| `not_found` | 作品不存在、已删除或私密 | 停下，告诉用户 |
| `unavailable` | 上游拒绝或故障（412、429、5xx、业务错误码） | 试下一个，并记一个有上限的冷却时间（INV-02） |
| `timeout` | 超出预算 | 试下一个 |
| `invalid_result` | 返回无法映射，例如没有媒体、身份对不上 | 试下一个，并记诊断码 |

- 每个失败都带一个安全的诊断码（大写字母、数字和下划线），不含 URL、Cookie 或密钥。
- 冷却从基础时长起按连续失败次数翻倍，不超过后台上限，内核另设 1 小时硬上限；到期自动恢复，不需要人工操作；成功一次即清零。冷却中的 Provider 被跳过，并记为 `cooling_down`，控制面可见。

### 2.3 路由（后台配置，A1）

每个平台一条 Provider 链，配置保存在后台：

| 配置 | 含义 |
|---|---|
| `order` | Provider 的顺序 |
| `policy` | `first_success` 或 `floor_and_upgrade`，见下 |
| `budget_seconds` | 前台总预算 |
| `floor_provider` | `floor_and_upgrade` 策略下的保底 Provider，例如 Native |
| `upgrade_window_seconds` | `floor_and_upgrade` 策略下，从开始解析起允许晚到结果替换的时长，不小于 `budget_seconds` |
| `platform_names` | 平台的显示名，用于识别“标题就是平台名”的占位值 |

两种策略：

- **`first_success`**：
  1. 按顺序调用，第一个成功的结果就用；
  2. 每个 Provider 拿到的是剩余的前台预算；
  3. 预算用完还没有结果，返回 `timeout`。
- **`floor_and_upgrade`**：
  1. 保底 Provider 从一开始就并行运行；首选 Provider 按顺序依次运行；
  2. 预算内首选 Provider 成功，就直接展示首选的结果；
  3. 预算到了还没有首选结果，先展示保底结果，标为 `provisional`；保底比预算晚到时，到达即展示；
  4. 之后第一个到达的首选结果：优于当前展示就替换，否则保留当前展示。两种情况下其余工作都结束（先到先得）；
  5. 首选 Provider 全部失败时，保底结果直接作为 `final` 展示；
  6. 升级窗口结束时，当前展示变为 `final`；
  7. “优于”按 1.4 第 2 条比较两份结果的最佳默认变体。

`floor_and_upgrade` 就是 INV-01 的通用写法，“先到先得”沿用 Human 的决定。代码里不写死任何平台的链，默认值放在数据迁移里。

内核里的 `ChainRun` 是这两种策略的唯一实现。它不调用 Provider、不计时：调度方启动它指定的 Provider，按时间顺序报告结果和时间，并展示它返回的结果。

### 2.4 健康测试

- 后台为每个平台配置样本链接（这部分已有）。
- “每个 Provider × 每个平台”的健康测试，做三件事：
  1. 只用这一个 Provider 解析样本，不走整条链（#116 已经这样做了）；
  2. 检查统一结果的不变式；
  3. 取默认变体的前 1KB（沿用已有的每日冒烟）。
- 工作台按统一结果显示字段覆盖：标题、封面、清晰度、大小各由谁提供。
- 统一结果缺少的事实按安全代码计数：视频或音频内容项的默认变体 `tracks = unknown` 时，记 `TRACKS_UNKNOWN`。

## 3. 交付规则：一张表，只看变体事实

按顺序检查，用第一条满足的：

| # | 条件 | 交付方式 |
|---|---|---|
| 0 | `drm = true`、`segmented = true`、`request_method` 不是 `GET`，或 `tracks = video_only` 却没有 `merge_with` | 不提供下载，显示原因：`DRM_PROTECTED`、`SEGMENTED_STREAM`、`UNSUPPORTED_REQUEST` 或 `NEEDS_AUDIO_MERGE`（同时满足时按这个顺序） |
| 1 | `tracks = video_only`（有 `merge_with`） | `server_merge`：服务端合并后交付 |
| 2 | `required_headers` 不为空 | `server_attachment`：服务端带上请求头取数，再转给用户 |
| 3 | 多个内容项一起保存（图片，以及实况照片的配对视频） | `browser_archive`：浏览器打包成 ZIP |
| 4 | 视频或音频，且 `browser_fetchable = true` | `browser_streaming`（Service Worker 流式保存）；失败时改用 `browser_blob`（上限 1 GiB，已知超出时不提供） |
| 5 | 单张图片 | `browser_direct` |
| 6 | `browser_fetchable = unknown` | 先试 `browser_streaming`；失败时改用 `server_attachment`（决定 1，后台可关闭） |
| 7 | 其他情况 | 不提供下载，显示原因 |

- 规则里不出现平台名、Provider 名或资源 ID 前缀。
- `tracks = unknown` 按完整文件处理：不命中第 1 条，按第 2～7 条交付。这与现状一致，只有明确分轨的资源才在服务端合并。
- 现有的例外都由事实推出：需要 Cookie 或鉴权的资源命中第 2 条；YouTube 高清音视频分离，命中第 1 条。B 站不因平台或常规的 Referer 一概走服务端（INV-03）。
- `server_attachment` 和 `server_merge` 计入现有的下载额度。
- 一起保存时（决定 2）：
  - 任一项命中第 0 条：不打包，显示原因；
  - 任一项需要合并：不打包，逐项交付；
  - 任一项需要请求头，或浏览器无法读取：服务端打包；
  - 任一项能否读取不确定：浏览器打包，失败时服务端打包（后台可关闭）；
  - 其余：浏览器打包。

## 4. 文件名（INV-06）

- **基础名：** 短标题。去掉非法字符，最长 80 个字符。没有标题时用 `平台_作品ID`。
- **多个内容项：** `基础名_序号`，序号从 1 开始、按 `index` 排列。实况照片的图片和视频共用一个序号；整个作品只有一组时不加序号。
- **扩展名：** 用变体 `container` 的真实扩展名；不确定时按响应的 Content-Type 推断；两者都没有时不生成文件名，永远不出现 `.bin`。
- **正文和话题** 不进入文件名。
- **打包下载：** `基础名.zip`。

## 5. 授权与安全（统一机制，第 2 步实现）

- 管线给每个变体签发一个短期授权，绑定 `url`、`host_policy`、作品和过期时间。下载入口只认这个授权。
  - 它取代现在各自独立的令牌：Provider manifest、legacy item、handoff、pair 等。
- 出站校验保持不变（逐跳校验、DNS 固定、主机白名单），按 `host_policy` 执行：
  - 每一跳都通过现有的出站安全检查：协议、公网地址（不接受内网、回环等地址）和 DNS 固定，规则与现在相同。原有的 HTTP 服务端附件路径不因本节改变（INV-03）；
  - `host_policy` 不为空时，每一跳的主机还必须匹配其中一个后缀，按点号边界匹配（`evil-cdn.com` 不匹配 `cdn.com`）；
  - `host_policy` 为空时，跳转到的主机不限后缀，但必须是通过上述检查的公网 HTTPS 主机。
- `required_headers` 的值只保存在服务端，浏览器拿不到。

## 6. 契约测试检查什么

全部用假 Provider 驱动，它们返回各种形状的统一结果或失败；时间是虚拟的。

- **路由：**
  - `first_success`；
  - `floor_and_upgrade`：预算内成功、超出预算、晚到结果替换、晚到结果不更好、保底晚于预算、首选全部失败、升级窗口结束；
  - 后台改顺序后行为跟着变；
  - 五种失败各自的链路行为，以及无法映射的结果；
  - 冷却时间有上限、到期自动恢复、只有 `unavailable` 触发冷却。
- **模型不变式：** 默认变体、占位值、分轨、轨道未知、分辨率标签、DRM 与分片流、请求方法、无合并对象的视频轨、字段覆盖。
- **交付：**
  - 第 3 节每一行一个用例；
  - 再加反例：同样的事实，换一个 Provider 名、平台或资源 ID 前缀，交付方式必须不变。
- **文件名：** 短标题、多项序号、实况照片共用序号、真实扩展名。
- **内核边界：** 内核代码里没有平台名、Provider 名或资源 ID 前缀，也不导入平台、Provider 或 Django 代码。

现有 `contracts/` 中 INV-01…09 的测试保留。

## 8. 已确认的决定（Human，2026-10-25）

1. 浏览器能否读取不确定时，失败后允许改由服务器转交：计入额度，并可在后台关闭。
2. 多图统一在浏览器打包，包括 gallery-dl 来源；只有浏览器无法读取时，才在服务器打包。
3. 晚到结果只要优于当前展示就替换，其余工作结束，与“先到先得”一致。
4. 单独的音频（例如抖音原声）作为可下载的内容项提供，但不设为默认。
5. 文件名长度上限 80 个字符。

实现时为落实以上条文补充了四个字段：`work_id`（第 4 节的“作品ID”）、`is_original`（1.4 第 2 条的“原画/源文件”）、`upgrade_window_seconds`（2.3 中晚到结果的截止时间）、`platform_names`（1.4 第 3 条的“平台名”）。它们不改变已确认的行为。

## 9. 已确认的修订

### D-01 轨道未知（Human，2026-10-25）

第 2 步盘点发现：天天、KuKuTool 的真实返回只有地址、大小和清晰度标签，没有音轨事实，而模型原先没有“未知”可写。Human 的决定：

> 批准 D-01 修订：tracks 增加 unknown 并作为默认值，按完整文件交付、计数 TRACKS_UNKNOWN；明确的 P 清晰度标签可以设 height。

据此修改了 1.3 的 `tracks` 和 `height`、1.4 第 4 条、2.4 和第 3 节的说明。适配器在上游或平台说明了轨道时，仍然必须写 `av`、`video_only` 或 `audio_only`。

### D-02 DRM 与分片流（Human，2026-10-25）

第 2 步 P3 发现：模型表达不了 HLS/DASH 分片流和 DRM，丢失这些事实后，它们会被当作普通文件在浏览器里流式保存。现状是旧选择器对两者都不提供下载（“此格式标有 DRM，不提供下载操作”“当前选择器不合并分片”）。Human 的决定：

> 批准 D-02 修订：变体增加 drm 和 segmented 事实，按现状不提供下载并显示原因；URL 是 .m3u8/.mpd/.m4s 却未标 segmented 则结果无效；优先选可下载的变体作默认。

据此修改了 1.3、1.4 第 2 条和新增第 6 条，以及第 3 节（新增第 0 条和一起保存的说明）。可下载优先同样用于 2.3 中判断晚到结果是否更好。内容项只有这类变体时，仍然展示，默认选其中最好的，下载处显示原因。在服务端拼接分片属于新的交付路径，不在本修订内。

### D-03 请求方法与 D-04 无合并对象的视频轨（Human，2026-10-25）

- **D-03：** 第 2 步 P4 发现：gallery-dl 的部分资源要用 POST 加请求体才能取到（已安装版本里是 `uploadir`），模型表达不了，会被当作普通 GET 直链。旧路径丢掉了这两个字段，会用 GET 去取（旧路径的问题，只记录）。
- **D-04：** P3 审查发现：yt-dlp 只给它自己选中的那一对音视频标了 `merge_with`。用户改选其他视频轨时，按原规则会在浏览器里下载成无声视频。旧选择器对这类格式不提供下载（“此格式需要合并音视频；当前选择器不将它当作完整文件下载”）。

Human 的决定：

> 批准 D-03/D-04 修订：变体增加 request_method（默认 GET），非 GET 不提供下载、原因 UNSUPPORTED_REQUEST，请求体的值不进入结果；没有合并对象的 video_only 不提供下载、原因 NEEDS_AUDIO_MERGE。

据此修改了 1.3、1.4 第 2 条、新增第 7 条，以及第 3 节第 0 条和一起保存的说明。不新增 POST 交付方式。给每条视频轨都配上最好的音轨、提供更多 YouTube 清晰度，会增加服务端合并，属于以后的产品决定。

### 更正：常规请求头（2026-10-26）

1.3 和第 3 节原先把 Referer 当作必须带的请求头的例子，并写了“B 站需要 Referer，命中第 2 条”。这与 Human 已确认的 INV-03 不一致：常规的 User-Agent、Accept、Referer、Origin 等请求头本身不构成必须的访问条件，B 站也不一概走服务端。现有代码同样如此（`request_context` 的常规请求头清单），第 2 步的适配器已经按它填写。本更正只改示例文字，不改变任何规则或行为。

细化（同日）：

- **常规请求头：** 上一段的“常规请求头不算”只指上游带了这些请求头的值的情况。上游明确列为必须的请求头，即使是常规请求头，仍然算 `required_headers`。这与现有代码一致（`request_context`：明确要求的常规请求头保留为限制）。
- **浏览器读不到：** 上游声明链接绑定 IP，或声明需要请求上下文却没有给出时，浏览器读不到，写 `browser_fetchable = false`。现有代码对这两种情况同样不让浏览器直连（INV-03 中的 IP 绑定和缺失上下文）。

两点都只是把现有的事实规则写清楚，不改变第 3 节的规则。

### D-06 跳转时允许的主机（Human，2026-10-26）

授权签名绑定了下载地址本身，所以第一跳一定是该地址的主机；`host_policy` 只决定跳转后还能去哪里。现状是：

- 有已知 CDN 清单的平台（抖音、B 站、小红书和固定的第三方规则），跳转后的最终主机仍必须在清单内（例如 `douyin.py` 的 `allowed_final_host_suffixes`）；
- 通用来源（yt-dlp、gallery-dl、ParseHub、videodl 面对任意网站）允许跳到任意通过逐跳检查的公网 HTTPS 主机（INV-03 契约说明）。

第 2 步 P3～P7 的适配器在没有清单时写了“只允许精确主机”，比现状更严，切换后会让跨主机的 CDN 跳转失败。Human 的决定：

> 同意：host_policy 为空表示任意通过逐跳安全检查的公网 HTTPS 主机，通用来源用空列表；非空列表每一跳都要匹配。

据此修改了 1.3 的 `host_policy` 和第 5 节的出站校验说明。有清单的平台继续沿用清单；没有清单时写空列表，不写精确主机。
