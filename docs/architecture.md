# Architecture

## Apps

- `search_app`: local image library search. It reads `static/images` and renders paginated image results.
- `xhs_download`: Xiaohongshu image/video parsing, preview proxying, and download API.
- `submissions`: submission form, uploaded cover image, list page, and detail page.

## Request Flow

`djangoProject/urls.py` routes:

- `/`: download site home
- `/xhs/`: Xiaohongshu parser UI
- `/xhs/results/`: Xiaohongshu parser results
- `/tiktok/`: Douyin parser UI
- `/tiktok/results/`: Douyin parser results
- `/media/proxy-image/`: preview image proxy
- `/media/download-images/`: selected media download API
- `/library/`: image library search
- `/library/results/`: image search results
- `/xhs_download/`: legacy Xiaohongshu redirect/API compatibility path
- `/submissions/submit/`: submission form
- `/submissions/list`: submission list

## Static and Media

- `static/`: application CSS/JS and the current local image library.
- `static/images/`: source image library plus generated `padded` images.
- `staticfiles/`: generated by `collectstatic`; do not edit manually.
- `media/`: uploads and downloaded assets in local development.

## Code Direction

Keep views thin over time:

- views: HTTP input/output, template context, JSON response
- services: parsing, downloading, image normalization, storage
- management commands: one-off or batch maintenance tasks
- tests: no import-time network or filesystem side effects

## Xiaohongshu Download Flow

The current download module keeps the `/xhs_download/` route as a stable UI entry while its parser layer is being prepared for multiple platforms. New parsing work should use the platform adapter shape instead of adding platform-specific logic to views.

- `services/assets.py`: shared `MediaAsset` and `ParseResult` data structures
- `services/candidates.py`: lightweight media candidate ranking/deduplication for platforms that expose multiple source URLs
- `services/provider_settings.py`: provider feature flags, provider order parsing, and optional external-provider credentials
- `services/quality.py`: lightweight HEAD/Range probing for reachable URLs, file size, content type, and final-host validation
- `services/diagnostics.py`: candidate diagnostics and probe-aware best-candidate selection used by provider research
- `services/registry.py`: choose the right platform adapter for a submitted URL
- `services/platforms/base.py`: platform adapter protocol
- `services/platforms/xiaohongshu.py`: Xiaohongshu URL support, HTML parsing, preview URL normalization, and media asset extraction
- `services/platforms/douyin.py`: Douyin URL support, embedded JSON extraction, native parser helpers, and ranked video candidate selection
- `services/platforms/douyin_providers.py`: Douyin provider orchestration, with disabled-by-default native-enhanced probing and native mobile feed/share/direct fallback
- `services/platforms/bilibili.py`: Bilibili URL support, BV/AV metadata lookup, public mp4 play URL extraction, candidate URL deduplication, and cover handling
- `services/platforms/ytdlp_generic.py`: optional disabled-by-default yt-dlp JSON runner and normalizer for generic third-party video fallback
- `services/platforms/gallerydl_generic.py`: optional disabled-by-default gallery-dl JSON runner and normalizer for generic third-party image/gallery fallback
- `services/platforms/external_tools.py`: shared subprocess environment, executable health, and short-lived cache helpers for external command providers
- `services/parser.py`: backward-compatible Xiaohongshu wrapper over the adapter layer
- `services/common.py`: filename cleanup, URL encoding, request retry, initial/final domain validation
- `services/downloads.py`: validate selected media, preserve original files by default, and build a temporary ZIP archive
- `services/download_tasks.py`: lightweight in-memory download task state for local/single-process ZIP progress
- `services/rate_limits.py`: Django-cache-backed request, concurrency, daily-count, and output-byte limits
- `management/commands/inspect_third_party_provider.py`: diagnostic command for allowlisted generic providers with provider manifest tokens hidden and provider media URLs redacted by default
- `views.py`: render pages, proxy preview images, and return ZIP download responses
- `djangoProject/health.py`: process liveness and dependency-backed readiness endpoints

The intended extension path for Douyin and future platforms is:

1. Add a new adapter under `services/platforms/`.
2. Register it in `services/registry.py`.
3. Return `ParseResult` with platform-neutral `MediaAsset` objects.
4. Reuse the existing preview proxy, original-file download, and ZIP archive pipeline.

Douyin support is intentionally scoped to stable no-login parsing at this stage. It handles common embedded JSON shapes, mobile share router data, mobile feed candidate URLs, and public play URL variants. Normal requests use the native provider. Ultra requests currently use KuKuTool as the only external upstream while fast native runs concurrently as fallback. TikHub and `native_enhanced` remain available for research and diagnostics but do not enter the synchronous web path.

Xiaohongshu does not currently need the same provider split because the stable path is still page HTML plus normalized media URLs. Keep it as a compact adapter until a second independent source, such as an app API or high-definition video provider, is introduced. Bilibili support currently uses the public view/playurl APIs for direct mp4 URLs; its `durl` values are treated as ordered source segments and only share candidate deduplication. DASH audio/video merge and higher-quality source selection should be added later as a separate provider layer that can enumerate candidate streams, probe size/bitrate, and fall back to the stable source without changing the adapter/view contract.

The generic third-party adapter is a fallback expansion path for platforms that do not yet deserve a dedicated adapter. KuKuTool can remain the first generic provider when `THIRD_PARTY_KUKUTOOL_PROVIDER_ENABLED=True`, but production can disable that path independently from the generic public-access switch and independently from Douyin ultra-HD's `KUKUTOOL_PROVIDER_ENABLED`. Each `ThirdPartyPlatformRule.provider_ids` tuple is both the allowlist and the platform-specific fallback order, so future platforms can prefer gallery-dl, yt-dlp, or KuKuTool independently from the global provider catalog. When `GALLERYDL_PROVIDER_ENABLED=True`, image/gallery platforms such as Imgur, Reddit, Tumblr, Flickr, and DeviantArt can fall back to `gallery-dl -J --no-download` and return allowlisted direct media URLs. Static resources become image assets; Imgur-style animated resources that resolve to `.mp4` or `.webm` become video assets so download content-type validation still matches. If gallery-dl exposes both original media fields and low-quality `thumbnail/preview` fields for the same gallery item, the normalizer keeps the original candidate and drops only that item's low-quality duplicate. Thumbnail-only items in a mixed gallery are still retained as fallback assets instead of being removed globally. When `YTDLP_PROVIDER_ENABLED=True`, video platforms such as YouTube, TikTok international, Instagram, Facebook, X/Twitter, and Kuaishou can fall back to `yt-dlp --dump-single-json`. If `YTDLP_MERGE_PROVIDER_ENABLED=True`, that same payload is inspected for a video-only + audio-only pair up to `YTDLP_MERGE_DEFAULT_MAX_HEIGHT`, currently 1080p; when that pair is better than the complete single-file candidate, the result becomes a signed `yt_dlp_merge` task that runs yt-dlp + ffmpeg during download. Both external command providers are off by default, run in bounded subprocess pools with minimal environments, isolated temporary working directories and temporary `HOME` values, sign provider download manifests, and reuse final-host download validation. The subprocess environment disables yt-dlp plugins and Python user-site packages, so deployments should install tools in the configured venv/system path instead of relying on a user home directory. Streaming manifests such as HLS/DASH are rejected until the product has explicit merge/transcode support. Known audio-only, video-only, and codec-ambiguous top-level `yt-dlp` formats are filtered out so the fallback does not return silent videos. YouTube merge is a normal technical requirement for many 1080p downloads, not only a 4K/8K feature. The UI "YouTube highest quality" switch raises the target to `YOUTUBE_MERGE_MAX_HEIGHT` for staff or public users allowed by settings, while the default path remains 1080p. These merge paths are suitable for local/staff validation; production should move the merge worker to Celery/RQ or an internal sidecar with persistent task state and stronger progress reporting.

Downloads are returned to the browser as ZIP files. The ZIP is built through a temporary file instead of keeping the whole archive in memory. Images default to original-file output so parsed source bytes are not re-encoded during normal use. Conversion helpers remain internal, but the current UI intentionally hides image format and quality controls to keep the product aligned with original-material backup.

The result UI follows a simple display contract: images stay visual-only because original quality is implied, while videos can show file size when the adapter or a lightweight probe can provide it. Local browser ZIP downloads can use an in-memory task to expose percent progress. Production disables that task path by default and the frontend falls back to a synchronous temporary ZIP response. A future production progress implementation must use a shared queue/state backend such as Redis plus Celery/RQ.

Signed generic third-party videos do not run the normal result-page size probe because their CDN hosts are intentionally scoped to provider manifests instead of the global media allowlist. They show provider-declared size when available and otherwise display unknown size until download progress starts. New provider manifest tokens bind the declared asset type when one is available; old tokens remain readable for compatibility, but newly generated preview and download paths include `type` so image/video and cover checks fail earlier in the manifest layer.

The server no longer accepts arbitrary client-provided filesystem paths. This keeps local development convenient while avoiding unsafe production behavior.

Ultra-HD provider settings are intentionally disabled by default. `ULTRA_HD_PROVIDER_ENABLED` controls provider availability, while `ULTRA_HD_PUBLIC_ACCESS_ENABLED` separately controls whether visitors may request it. Local development settings can come from the project-root `.env`; deployment should use environment variables or secret storage. Production mode requires real secret/host values and a shared Redis cache.

The KuKuTool provider invokes a bundled Node.js helper that performs the upstream protocol exchange and returns `video_fullinfo`. KuKuTool and native use separate bounded executors. The request thread only arbitrates for three seconds: an in-budget KuKuTool result wins, otherwise a completed native result is returned while the bounded KuKuTool task continues to populate cache. Redis single-flight deduplicates the same `aweme_id` across workers, and a Redis concurrency counter caps total upstream work. Candidates are restricted to ByteDance CDN hosts, deduplicated by stable TOS object path, and ranked by bitrate, declared size, and quality fields.

The yt-dlp and gallery-dl generic providers are intentionally simpler than the KuKuTool provider in this iteration. They are optional breadth tools, not replacements for dedicated adapters. Their subprocess timeout is capped by the smaller of the provider-specific timeout and the platform frontend budget, so a synchronous page parse cannot accidentally wait for the full external-command timeout when the frontend budget is lower. Most platforms use `THIRD_PARTY_FRONTEND_TIMEOUT_SECONDS`; YouTube uses `YOUTUBE_FRONTEND_TIMEOUT_SECONDS` because cold yt-dlp extraction commonly exceeds three seconds. Each subprocess runs with a temporary cwd and temporary `HOME`, and its JSON stdout/stderr is written to temporary files and rejected when it exceeds `THIRD_PARTY_EXTERNAL_OUTPUT_MAX_BYTES`, which keeps malformed or unexpectedly huge extractor output from being buffered into Django worker memory. The generic adapter also treats the frontend timeout as the total fallback budget: if one provider consumes the budget, the request stops instead of trying the next external tool. Before broad public traffic, move them behind long-running sidecars or a shared job queue so process startup, extractor updates, rate limits, and cookies are isolated from Django web workers.

MeTube is a useful architectural reference for the future queue layer because it wraps yt-dlp behind a browser UI, bounded concurrency, persistent task state, progress hooks, and deployment-focused environment settings. Treat it as a product and operations reference rather than source to copy into this Django app. The current project should keep its own adapter/provider contract and implement the production download path with Redis plus Celery/RQ or an internal sidecar; this avoids coupling the parser UI to MeTube's full Web app shape. External tools should be invoked as pinned commands or sidecars, not vendored source. Review licenses before distribution: yt-dlp source is currently Unlicense, though packaged builds can include extra third-party notices; gallery-dl is GPL-2.0 and its GitHub project points active development toward Codeberg; MeTube is AGPL-3.0.

Generic third-party parsing records timing and fallback diagnostics on every synchronous web parse. Failed attempts emit `third_party_provider_failed`, successful selection emits `third_party_provider_selected`, and the returned `ParseResult.metadata` includes `selected_provider`, `selected_provider_duration_ms`, `provider_total_duration_ms`, `provider_attempts`, and `provider_fallback_count`. `selected_provider_duration_ms` measures only the provider that produced the selected result; `provider_total_duration_ms` measures the whole provider chain including failed fallback attempts. `inspect_third_party_provider --json` mirrors the attempt chain at the top level on success and failure, includes the normalized `source_url` plus matched `platform_id` whenever they are known, and adds a `smoke` summary with `recommended_rollout`, duration budget, asset count, media types, and issues. Input or configuration failures, including missing URLs, unsupported URLs, disabled providers, and invalid binary overrides, return an empty `attempts` list with `status: "rejected"`. Provider manifest tokens are never printed, and provider media URLs or URLs embedded in error text are redacted by default; `--show-urls` is reserved for local manual verification. Plain text output prints the normalized URL, platform id, and a compact attempts list for terminal triage. These fields are intentionally kept out of the user-facing UI but make it possible to distinguish upstream timeout, extractor schema drift, host allowlist rejection, and normal fallback behavior from server logs or management-command output.

External command providers expose static runtime health before parsing starts. `yt-dlp` and `gallery-dl` health includes whether a binary was explicitly configured, which executable would be launched, whether it resolves on disk/PATH, and whether the provider is ready. Django system checks require explicit binaries in production and report missing executables whenever the optional provider is enabled. YouTube merge diagnostics additionally report ffmpeg readiness, maximum merge height, output size cap, task timeout, and whether the public/staff switches make the merge path available to visitors.

KuKuTool generic and the external command providers also keep best-effort short-lived payload and failure caches keyed by the normalized source URL. Payload cache hits avoid repeated upstream tasks or subprocess startup for the same public link. Failure cache hits return a retryable provider timeout quickly, which protects bounded worker pools when a specific upstream page is broken, unsupported, or temporarily blocked. Cache read/write failures are logged but do not block the real provider attempt. When a signed generic-provider preview or download fails with a recoverable HTTP, HTML-body, or content-type error, the matching provider/source payload and failure caches are invalidated so the next parse can obtain a fresh direct URL instead of being short-circuited by stale state. These caches are intentionally short-lived and are not replacements for a durable queue or sidecar.

The generic third-party web entrypoint applies both per-IP and global fixed-window request limits before provider execution. KuKuTool generic, yt-dlp, and gallery-dl therefore share the same public traffic guardrail even though each provider still keeps its own worker and timeout controls internally.

The public download APIs are explicitly CSRF-protected and use shared-cache limits for per-IP frequency, per-IP concurrency, daily request count, and output bytes. The preview image proxy has an independent request/byte budget because it also fetches and serves external media. In-memory asynchronous tasks are disabled by default outside development. Django only serves `MEDIA_ROOT` through `MEDIA_URL` while `DEBUG=True`; production media delivery belongs to Nginx or controlled object storage.

Runtime health is split into liveness and readiness. Liveness only proves the Django process can answer, while readiness performs cache and database round trips so a deployment platform can stop routing traffic when Redis or the database is unavailable.

Current limitation: KuKuTool uses an undocumented third-party protocol and signed CDN URLs. Profile discovery can recover from some upstream field rotations and caches a successful profile across helper processes, but availability and rate limits remain outside this project. The helper limits discovery response sizes and only follows same-origin redirects. There is still no persisted timing dashboard, shared durable task queue, or long-running Node sidecar.

SSRF protection validates URL schemes, host suffixes, localhost/private literal IPs, and redirect final hosts. This is acceptable for the current fixed major-platform CDN allowlist. If future providers allow operator-defined domains, add DNS resolution checks before requests, reject resolved private IPs, and repeat checks after redirects to reduce DNS rebinding risk.

The download implementation still has duplicated image/video/cover handling between ZIP and server-folder save paths. A future download pipeline should introduce a shared `DownloadOutput` resolver so single-file downloads, object storage, deduplication, and optional conversion/transcoding can reuse the same output planning logic.

Douyin candidate research can be inspected with:

```bash
.venv/bin/python manage.py inspect_douyin_candidates "https://v.douyin.com/xxxx/" --json
.venv/bin/python manage.py inspect_douyin_candidates --health --json
```

The command compares direct page, mobile feed, and mobile share candidates and records declared size, probed size, source field, quality label, final host, content type, and probe errors. Its `--health` mode skips URL parsing and reports the Douyin ultra-HD settings, KuKuTool runtime, optional sidecar health, circuit state, and configuration issues.

Generic third-party providers can be inspected with:

```bash
.venv/bin/python manage.py inspect_third_party_provider --health --json
```

This health mode does not require a URL. It reports the generic public-access switches, concrete provider health, per-platform provider coverage, and actionable issues such as a public entrypoint with no enabled provider or an enabled external command provider whose binary is not ready. Plain text output lists coverage per platform for manual triage; JSON output separates each rule's `provider_ids` from the currently active `enabled_provider_ids` and `ready_provider_ids`. The command and admin provider-health JSON both include a `rollout` object with `disabled`, `hold`, `staff_only`, or `public_candidate` status so release checks do not rely on several booleans being read together. The admin provider-health JSON also includes `provider_states` so a staged Provider can show as individually ready even when the global public entrypoint is still disabled; `public_ready` remains the field that combines provider readiness with the global and public-access switches, while `public_candidate` still requires product approval and platform-specific smoke evidence before broad traffic. KuKuTool generic cache reads are best effort in this diagnostic path: Redis errors are returned as `cache_error` instead of polluting JSON output with tracebacks. When `--health` is paired with an explicit `--provider ytdlp` or `--provider gallerydl` plus `--binary`, the command probes that binary version even if the Provider is not enabled yet.

```bash
.venv/bin/python manage.py inspect_third_party_provider "https://www.youtube.com/watch?v=..." --provider ytdlp --binary ".venv/bin/python -m yt_dlp" --json
```

Add `--show-urls` only when a local smoke test needs the complete provider CDN URL for manual verification.

```bash
.venv/bin/python manage.py inspect_third_party_provider "https://imgur.com/..." --provider gallerydl --binary ".venv/bin/python -m gallery_dl" --timeout 8 --json
```

The command uses the same platform allowlist and normalizer path as the web adapter, but summarizes provider results without exposing internal provider manifest tokens. `--provider auto` respects the current enabled-provider flags and mirrors web fallback order; explicit provider values bypass enabled flags so a disabled provider can still be diagnosed in isolation. `--timeout` overrides both the diagnostic frontend budget and the selected provider timeout, while the web path still keeps `THIRD_PARTY_FRONTEND_TIMEOUT_SECONDS` as the user-facing deadline. `--health` can also accept `--provider ytdlp --binary ...` or `--provider gallerydl --binary ...` to verify a temporary executable path before writing it into `.env`. Gallery-dl cold parses can exceed the default three-second web budget, so staged image/gallery rollout should either raise the generic frontend budget deliberately or move this path behind a sidecar/job queue.

For local development, server-side save can be enabled with environment variables:

- `XHS_ALLOW_SERVER_SAVE=True`
- `XHS_ALLOW_ABSOLUTE_SAVE_PATH=True`
- `XHS_DEFAULT_SERVER_SAVE_DIR=xhs`

When server-side save is disabled, the UI falls back to browser ZIP download only.
