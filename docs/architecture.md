# Architecture

## Apps

- `search_app`: local image library search. It reads `static/images` and renders paginated image results.
- `xhs_download`: Xiaohongshu image/video parsing, preview proxying, and download API.
- `submissions`: submission form, uploaded cover image, list page, and detail page.

## Request Flow

`djangoProject/urls.py` routes:

- `/`: download site home
- `/xhs/`: Xiaohongshu parser UI
- `/xhs/results/`: Xiaohongshu parser results
- `/tiktok/`: Douyin parser UI
- `/tiktok/results/`: Douyin parser results
- `/media/proxy-image/`: preview image proxy
- `/media/download-images/`: selected media download API
- `/library/`: image library search
- `/library/results/`: image search results
- `/xhs_download/`: legacy Xiaohongshu redirect/API compatibility path
- `/submissions/submit/`: submission form
- `/submissions/list`: submission list

## Static and Media

- `static/`: application CSS/JS and the current local image library.
- `static/images/`: source image library plus generated `padded` images.
- `staticfiles/`: generated by `collectstatic`; do not edit manually.
- `media/`: uploads and downloaded assets in local development.

## Code Direction

Keep views thin over time:

- views: HTTP input/output, template context, JSON response
- services: parsing, downloading, image normalization, storage
- management commands: one-off or batch maintenance tasks
- tests: no import-time network or filesystem side effects

## Xiaohongshu Download Flow

The current download module keeps the `/xhs_download/` route as a stable UI entry while its parser layer is being prepared for multiple platforms. New parsing work should use the platform adapter shape instead of adding platform-specific logic to views.

- `services/assets.py`: shared `MediaAsset` and `ParseResult` data structures
- `services/candidates.py`: lightweight media candidate ranking/deduplication for platforms that expose multiple source URLs
- `services/provider_settings.py`: provider feature flags, provider order parsing, and optional external-provider credentials
- `services/quality.py`: lightweight HEAD/Range probing for reachable URLs, file size, content type, and final-host validation
- `services/diagnostics.py`: candidate diagnostics and probe-aware best-candidate selection used by provider research
- `services/registry.py`: choose the right platform adapter for a submitted URL
- `services/platforms/base.py`: platform adapter protocol
- `services/platforms/xiaohongshu.py`: Xiaohongshu URL support, HTML parsing, preview URL normalization, and media asset extraction
- `services/platforms/douyin.py`: Douyin URL support, embedded JSON extraction, native parser helpers, and ranked video candidate selection
- `services/platforms/douyin_providers.py`: Douyin provider orchestration, with disabled-by-default native-enhanced probing and native mobile feed/share/direct fallback
- `services/platforms/bilibili.py`: Bilibili URL support, BV/AV metadata lookup, public mp4 play URL extraction, candidate URL deduplication, and cover handling
- `services/parser.py`: backward-compatible Xiaohongshu wrapper over the adapter layer
- `services/common.py`: filename cleanup, URL encoding, request retry, initial/final domain validation
- `services/downloads.py`: validate selected media, preserve original files by default, and build a temporary ZIP archive
- `services/download_tasks.py`: lightweight in-memory download task state for local/single-process ZIP progress
- `services/rate_limits.py`: Django-cache-backed request, concurrency, daily-count, and output-byte limits
- `views.py`: render pages, proxy preview images, and return ZIP download responses
- `djangoProject/health.py`: process liveness and dependency-backed readiness endpoints

The intended extension path for Douyin and future platforms is:

1. Add a new adapter under `services/platforms/`.
2. Register it in `services/registry.py`.
3. Return `ParseResult` with platform-neutral `MediaAsset` objects.
4. Reuse the existing preview proxy, original-file download, and ZIP archive pipeline.

Douyin support is intentionally scoped to stable no-login parsing at this stage. It handles common embedded JSON shapes, mobile share router data, mobile feed candidate URLs, and public play URL variants. Normal requests use the native provider. Ultra requests currently use KuKuTool as the only external upstream while fast native runs concurrently as fallback. TikHub and `native_enhanced` remain available for research and diagnostics but do not enter the synchronous web path.

Xiaohongshu does not currently need the same provider split because the stable path is still page HTML plus normalized media URLs. Keep it as a compact adapter until a second independent source, such as an app API or high-definition video provider, is introduced. Bilibili support currently uses the public view/playurl APIs for direct mp4 URLs; its `durl` values are treated as ordered source segments and only share candidate deduplication. DASH audio/video merge and higher-quality source selection should be added later as a separate provider layer that can enumerate candidate streams, probe size/bitrate, and fall back to the stable source without changing the adapter/view contract.

Downloads are returned to the browser as ZIP files. The ZIP is built through a temporary file instead of keeping the whole archive in memory. Images default to original-file output so parsed source bytes are not re-encoded during normal use. Conversion helpers remain internal, but the current UI intentionally hides image format and quality controls to keep the product aligned with original-material backup.

The result UI follows a simple display contract: images stay visual-only because original quality is implied, while videos can show file size when the adapter or a lightweight probe can provide it. Local browser ZIP downloads can use an in-memory task to expose percent progress. Production disables that task path by default and the frontend falls back to a synchronous temporary ZIP response. A future production progress implementation must use a shared queue/state backend such as Redis plus Celery/RQ.

The server no longer accepts arbitrary client-provided filesystem paths. This keeps local development convenient while avoiding unsafe production behavior.

Ultra-HD provider settings are intentionally disabled by default. `ULTRA_HD_PROVIDER_ENABLED` controls provider availability, while `ULTRA_HD_PUBLIC_ACCESS_ENABLED` separately controls whether visitors may request it. Local development settings can come from the project-root `.env`; deployment should use environment variables or secret storage. Production mode requires real secret/host values and a shared Redis cache.

The KuKuTool provider invokes a bundled Node.js helper that performs the upstream protocol exchange and returns `video_fullinfo`. Candidates are restricted to ByteDance CDN hosts, deduplicated by stable TOS object path, and ranked by bitrate, declared size, and quality fields. A complete, unexpired structured candidate is accepted directly; incomplete metadata is verified with a Range request. Validated signed URLs are cached through Django cache with TTL bounded by the URL expiry time.

The public download APIs are explicitly CSRF-protected and use shared-cache limits for per-IP frequency, per-IP concurrency, daily request count, and output bytes. The preview image proxy has an independent request/byte budget because it also fetches and serves external media. In-memory asynchronous tasks are disabled by default outside development. Django only serves `MEDIA_ROOT` through `MEDIA_URL` while `DEBUG=True`; production media delivery belongs to Nginx or controlled object storage.

Runtime health is split into liveness and readiness. Liveness only proves the Django process can answer, while readiness performs cache and database round trips so a deployment platform can stop routing traffic when Redis or the database is unavailable.

Current limitation: KuKuTool uses an undocumented third-party protocol and signed CDN URLs. Profile discovery can recover from some upstream field rotations, but availability and rate limits remain outside this project. The code emits structured provider logs for failures, validated-cache hits, probe duration, selected provider, and fallback reason, but there is not yet a persisted timing dashboard or cross-worker single-flight lock.

SSRF protection validates URL schemes, host suffixes, localhost/private literal IPs, and redirect final hosts. This is acceptable for the current fixed major-platform CDN allowlist. If future providers allow operator-defined domains, add DNS resolution checks before requests, reject resolved private IPs, and repeat checks after redirects to reduce DNS rebinding risk.

The download implementation still has duplicated image/video/cover handling between ZIP and server-folder save paths. A future download pipeline should introduce a shared `DownloadOutput` resolver so single-file downloads, object storage, deduplication, and optional conversion/transcoding can reuse the same output planning logic.

Douyin candidate research can be inspected with:

```bash
python manage.py inspect_douyin_candidates "https://v.douyin.com/xxxx/" --json
```

The command compares direct page, mobile feed, and mobile share candidates and records declared size, probed size, source field, quality label, final host, content type, and probe errors.

For local development, server-side save can be enabled with environment variables:

- `XHS_ALLOW_SERVER_SAVE=True`
- `XHS_ALLOW_ABSOLUTE_SAVE_PATH=True`
- `XHS_DEFAULT_SERVER_SAVE_DIR=xhs`

When server-side save is disabled, the UI falls back to browser ZIP download only.
